# Mid-quest resume contract

This is the admission and continuation contract for the restored quest roster after genuine Tower completion. The source contract packet maps native and installed routes, saved branch fixtures and the scoped exceptions. Runtime qualification follows the native capture and handoff. [Current contract review](../prealpha/quest_resume_contracts_rc2_20261114_01/REPORT.md) · [Exceptions](quest_resume_exceptions.md)

## Scope and decision

The final 15 November selection permits new resume implementation for only four stage types: earned items waiting for collection, travelling somewhere or waiting to talk, simple timers, and multiple unfinished objectives. All other interruption states are omitted, including pending message delivery/read/replies, call handoffs, active playback or encounters, escrow and unresolved transfers. Classify the complete cooperating state; a timer or parallel objective does not qualify if an inseparable excluded pending branch must also be restored. An idle shared phone-support listener alone is not an interrupted message or call; distinguish ordinary support from pending execution. Existing reviewed adapters retain their bounded support. Native messages, calls and encounters may start normally after a supported boundary resumes. [Selected scope and omission notes](mid_quest_resume_four_types_20261115.md)

The coverage goal is every eligible interruption across quests when the actual pending state fits one of the four types. A quest can qualify at multiple execution points. The 160 mapped gigs and side/minor jobs are the first source inventory for coverage review. The 15 separately scoped records and 43 scanner/cyberpsycho activities retain their existing content admission. The four whole-quest exceptions, five earlier narrower exceptions, category-level omissions and recorded Falco/Reyes message-stage exclusion still apply. A new exception needs the affected stage or branch, exact blocker, preserved progress and available fallback. Unknown state remains a pending qualification finding.

For a selected quest, the dispatcher returns exactly one of these decisions:

| Decision | Required evidence | Effect |
| --- | --- | --- |
| Preserve terminal | Verified genuine completion or failure | Leave the history, owner outcome and existing receipts intact. Never reissue setup or rewards. |
| Continue exact | State within one of the four selected types, same-ending-session checkpoint, verified original owner and resource identities, coherent pending state, retired old callback path, and sole qualified continuation owner | Restore the original logical handlers with their saved state and let the authored graph advance. |
| Keep existing owner | A proved live native or private owner already controls the state | Do not start a second controller. |
| Fresh entry | Never-started history and existing earned prerequisites | Use the currently reviewed native/private start, not a resume checkpoint. |
| Stage fallback | Older post-Tower save with a reviewed earned-stage adapter whose exact predicates pass | Begin at that reviewed stage start. Record this separately from exact continuation. |
| Defer | Missing, contradictory or unsupported state, or a documented exception | Preserve the save and normal Tower cleanup; do not fabricate history, replay setup or force a gate. |

## Shared discovery and handoff

Build candidate plans from the verified same-session checkpoint and the matching authored quest graphs. Use the captured phases, listener types, active inputs and branch state to discover the interruption point and its cooperating owners. Source data supplies native dependencies, journal bindings and existing ownership and reward constraints. Apply the same classification and restore rules wherever those native mechanisms recur.

Use one runtime transaction for all qualified plans. Its inputs carry the checkpoint state and source-derived data, including each affected owner, required support and mutation scope. Qualify a separate decision for each cooperating family, and coordinate families that share a lease or owner. A newly encountered eligible quest or another eligible point in the same quest should exercise the same code through its source data. Keep quest names and individual stages in fixtures and source records. Use the exception process for cases that require special handling.

## Checkpoint required before destructive cleanup

The checkpoint belongs to the ending session and is committed before the existing q307/q115 history gate acknowledges. It records the route, gate ticket, quest-system generation, save-local schema and exact resource/provider identities. The global-latest history file remains evidence for existing adapters; it cannot substitute for this checkpoint.

For every active owner selected for continuation and its cooperating family, the checkpoint must carry the following state. Broad diagnostic capture may include excluded classes; capture alone does not qualify them for restoration.

1. **Execution address and ancestry:** original root and full phase path, node ID, handler type, registration and owner generation, active parent/child relationships, resource hashes and the approved Johnny-edited route. Cached paths, a killed fact and an Active journal are not owner proof.
2. **Progress and branch state:** all relevant journal states, optional/tracked bits and counters; accepted choices and outcome facts; native node-instance stores, pending inputs, logical AND/OR/XOR latches and parallel handlers. A single objective name cannot reconstruct these.
3. **Pending work:** real-time and game-time waits with remaining duration, callback identity, pending quest notifications and the collection, travel/talk or parallel-objective listeners within scope. Identify each callback producer and consumer. Detect excluded pending message/call, playback, encounter and transfer state so that an inseparable family defers; implementing serialization or restoration of those excluded states is not required.
4. **Support ownership:** root and nested phase-prefab tickets, instance prefabs, actors, communities, NodeRefs, scene/camera/workspot and phone listeners, shared leases, external mod owners and cleanup obligations. Saved activation flags alone do not prove physical presence or a live owner.
5. **One-time effects:** inventory and escrow state, existing reward and cleanup receipts, counters and achievements, granted access, already-issued messages and completed setup. Use native execution state and pending operations to distinguish unissued, pending and committed effects. Preserve an unknown receipt as unknown and defer an active handoff if its effect would risk replay.

Each field is class-specific and must preserve its native identity. If a needed field has no safe reader or serializer, exact continuation of that state defers. Under the revised scope, implementing every such field is not a release requirement. A scope exception and a temporary evidence gap must be recorded separately. Source graph reachability is only a candidate route; the captured native latches and owner state determine which branches were actually active.

## Suspension and restore transaction

At the pre-cleanup boundary, the quest and delay workers must agree on one cutoff. An expiry that wins the race follows the original graph; a failed hold returns the still-valid original timer and lets normal ending behavior proceed. After a successful hold, prove the callback producers stopped, clear or reserve their old notification slots through a complete worker pass, and persist only value data when native retirement destroys an owner. Saves made during this interval require a defined barrier or a complete checkpoint; an index that could still receive an old callback cannot be reused.

The Tower, its final scenes, credits and native cleanup then run normally. After genuine completion, revalidate resource/provider hashes, original ancestry, required support and the current state against the four selected types. Recheck any successor reached by natural expiry before retirement. If that successor needs an excluded pending state, defer the affected family without restoring the earlier timer or skipping prerequisites. Recreate one original logical owner or a cooperating family with the saved branch and pending state. Reattach each timer with the captured remaining duration and verify an actual scheduler record, callback target and node-to-timer mapping. A returned timer ID alone is not success. Restore required support, actors and leases only through qualified native paths. If the handoff needs an excluded pending phone, scene, encounter or transfer state, defer that inseparable family. Keep ordinary later native progression and do not replay earlier setup, fights or rewards. On any conflict or partial failure, unwind the new owner and defer. Existing adapters must not claim the same cooperating family during an active handoff or partial rollback. A previously reviewed fallback can apply only after the conflicting new owner is fully unwound and the fallback's own predicates pass.

The continuation receipt is committed only after the restored owner and all required callbacks are bound. Save/reload must use native serialization for the resumed handler, timers and support, and must not issue a second callback, briefing or payout. Keep persisted node, resource, field and receipt names stable for future upgrades.

## Qualification rule

The Step 1 packet provides source routes, state requirements and remaining evidence boundaries. Step 3 verifies the prototype transaction with Cassius. In Step 4, qualify the common discovery and restore path with different quests and distinct interruption points, including cases outside the original development fixtures. Run those cases through the same runtime code, with differences supplied by their checkpoint and source data. Cover both clock types, concurrent waits, partial joins and exclusions. The live handoff through genuine Tower cleanup is the final acceptance check in Step 5, after all four types pass offline.

A state is **runtime qualified** after its original owner, support, branch and receipt evidence pass the live transaction, actual objective advancement and save/reload. Use compatible base-game and EP1 cases, with inactive, terminal, excluded and existing-owner controls. Record the exact fixtures, unqualified resource variants and deliberate exclusions. The Falco/Reyes pending-message pilot remains outside scope. [Roadmap](../ROADMAP.md#mid-quest-resume-after-the-tower)
