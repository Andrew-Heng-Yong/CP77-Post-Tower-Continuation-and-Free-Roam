# Independent Skippy runtime review

SC2 cannot recover the user's captured save. `ManualSave-23` already contains `PTFRSKIP_Ambient_Claimed=1`, `Entered=1`, `Stopped=1`, with no `Stop` fact, before SC2 was installed. Its save timestamp is 22:48:59; SC2 installation was at 22:49:36. The new SC2 telemetry at 22:52:10 reproduces that state. SC2's request predicate requires all four receipt/control facts to be zero, so wider body/history eligibility cannot resolve this state.

The cause is the SC1 wrapper's handling of native `TurnOff`. The native MQ007 ambient child returns `TurnOff` through a terminating child output when Skippy is unequipped. The native parent sends that output back to its equipped-Skippy wait and starts the ambient child again when equipped. SC1 instead connects `TurnOff` to `Stopped=1` and its own terminating output. The scope of termination thus grows from one ambient activation to the entire private owner. These are source-proven lifecycle errors; the save and latest log match the resulting dead-end. They do not by themselves prove every missing line or rendering problem.

The proposed SC3 version keeps the old saved facts and resource intact. An old `Stopped=1` is usable because the sole writer has only the native termination and explicit cut branches as predecessors and immediately flows to the wrapper's terminating output. An active old owner must take its existing stop/cut path and acknowledge `Stopped`; an unclaimed old owner has its pending Request cleared and Stop latched before SC3 is admitted. Clearing old `Stopped` on a terminated save would remove the only receipt and cannot revive its dead watcher.

SC3 owns one persistent nested loop containing both the native equipped-Skippy wait and original ambient child. Normal `TurnOff` clears only new telemetry `Active`, then returns to the equipped wait. A one-time story takeover cuts the whole loop, including pending admission; only that cut writes SC3 `Stopped`. Both S23 one-time owners must wait until that acknowledgement before issuing. There are no Skippy native fact, mode, reward, journal or item resets.

The original ambient payload includes the expression reset/controller, gameplay comment phase, exact Skippy item conditions, both native reaction and return scene dependencies, hologram prefab and the `#mq007_01_skippy_prop` attach/detach operations. These are preserved rather than recreated. The reaction scene contains native dialogue events. The comment phase's Skippy/ammo add nodes42/43/45 belong to isolated `SkippyTestIn` input39 and are unreachable from ordinary `In1`, which is the only input the native ambient parent invokes. Normal ItemManager21 retains original weapon Shoot behavior. All five calls into the return scene use `SkippyNoReturnOneliner`, each behind the false branch of `mq007_skippy_goes_emo==0`; the captured save has absent/zero emo, so these refusal lines are excluded in that fixture. This is not a newly admitted delivery/reward root. Current archive winner and prefab runtime binding are separate packaging/runtime checks; offline equality cannot establish visible hologram or audible speech.

`verify_01.py` independently evaluates the serialized guard and extracted source predicates against saved and adversarial states. It includes the actual SC2 source as a negative control, the old terminal edge as another negative control, a missing migration branch negative control, and repeated equip/unequip plus takeover event sequences. Native candidate 01 was withheld by the native reviewer because DeepCopy left shared socket references; only candidate 02 is eligible for the final proof. The lifecycle sequence model covers ownership boundaries and abstracts native timing; it is not an engine execution test.

All work is workspace-only or read-only. No game launch, installed edit, fact write, save edit or user test request was made.
