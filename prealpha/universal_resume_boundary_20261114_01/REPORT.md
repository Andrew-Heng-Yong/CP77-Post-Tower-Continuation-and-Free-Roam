## Remaining implementation

The timer must be removed from the old scheduler under a verified suspension boundary and committed to an ending-session checkpoint before the gate releases. The current observer leaves the original owner and callback running. To turn this into a handoff, the quest job must acknowledge ownership and settle any queued notification, while the delay job claims the pending timer before expiry. A failed claim must leave the original ending and quest progression available.

After genuine cleanup, revalidate the original ancestry and support, then recreate the wait with its captured duration and let the native handler emit exactly one notification. The ordinary scheduler registration API can return an allocated serial even if its pending insertion ring is full. Its returned ID therefore cannot be the success receipt for a restore. The worker must independently confirm that the new slot exists before the restore commits. The normal reload initializer's stale-ID path can mark a handler ready immediately if callback attachment fails, so that path needs its own guarded transaction. Both clock types, concurrent waits and the base-game/EP1 owner cases still need live qualification.
