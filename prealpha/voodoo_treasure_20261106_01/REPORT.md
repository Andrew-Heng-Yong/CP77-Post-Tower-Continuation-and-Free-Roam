# Voodoo Treasure investigation

**The door, keypad, stash shell and loot container are now bound to their cooked placements and exact persistent records.** QR19 calls the original stash phase. Its admission still cannot establish whether a closed stash has been claimed before. The current evidence identifies a replay risk and a native cleanup class discrepancy. A duplicate reward or failed cleanup has yet to be observed.

### What cleanup can do

Native node `4` asks for `TerminalControllerPS.ForceDisabled` on the keypad. Native node `21` asks for the same class and action on the **door**, whose only observed corresponding state is `DoorControllerPS`. The two classes have separate inheritance branches. The current device manager passes the requested class to native lookup. In that lookup, the materialized-state fast path can return the existing record before the requested-class comparison used on serialized hydration. The next cast is to shared `gameDeviceComponentPS`, and `GetQuestActionByNameToNative` can build the inherited `ForceDisabled` action on a returned door PS. A type difference alone therefore cannot predict whether this cleanup fails in the loaded case. The cold lookup uses the requested class in its compatibility and creation paths. Actual lookup selection, event delivery and the real post-action state remain unobserved. [Native trace](native_trace.json), [pinned script capture](../quest_restoration_qr7/worker_c/native_scripts_02/result.json)

The stock `OnQuestForceDisabled` disables the device without writing `m_isOpened`. A disabled door rejects ordinary toggle/close. Walking out cannot close this door automatically because the placed setting is off. There is a native close transition on an enabled open door through `OnToggleOpen`; authorized requests can queue `ToggleOpen` for an unlocked door. Whether a normal post-claim interaction on this particular door remains available after both cleanup actions is still a live question. A successful keypad password attempt writes a fact named for that password. Its value can support authorization history and has no connection to the loot claim.

## Loot and saved history

The placed container override enables area loot, has no explicit loot tables or content assignment and starts with its quest mark set. The template defaults alone would have missed the area-loot override. A quest mark, ordinary loot or the empty state does not identify an earlier claim of the three injected items.

The pinned binary's `gameContainerManager+0x258 → 0x1527428 → 0x7AF278` appends a descriptor to a loaded entry, or to a pending per-entity list when the entry is absent. The loaded branch constructs `gameeventsReloadLootEvent` at `0x2B39FEC` and sends it through `0xF05C44`. Registration `0x11575D8 → 0x1157F90` binds the callback `0x2AE4DF4`. It looks up `gameIContainerManager` and `gameILootManager`. The container virtual `+0x290 → 0x884090` reads the loaded descriptor array, and the callback processes the resulting list through the loot virtual `+0x1D0 → 0x218DBF0` and the container's inventory operations. This closes the previous dispatch gap up to the actual reload consumer. Exact existing-item matching, removal/addition policy, pending-list persistence and whether a historical emptied inventory can regenerate the money, shard or Rook remain unresolved. An append is not a grant. [Native trace](native_trace.json)

The 26 October AutoSave-16 backup and 4 November AutoSave-8 both match all four key/class pairs. Both parse with the door closed and ON, keypad ON, and the authored loot quest mark still set. Neither contains a selected password fact, information-download fact, or private Issued/Entered/Finished record. AutoSave-8 stores Ready=1 and Permit=0. Neither parsed inventory exposes a matching subinventory ID. These are bounded save snapshots. Missing rows are serialized absence, the reader may materialize defaults, and the files do not demonstrate an earlier stash claim, exact chronology, or executing quest ownership. The facts, PS2 metadata and file hashes were captured read-only. [Saved evidence](saved_02.json)

## Playtest qualification

- **Ordinary unclaimed stash.** Use a disposable, genuine Tower continuation with a never-opened stash and eligible Inactive journal history. Record whether the information was earned beforehand. Approach with the door still closed. Check that the private owner has Entered before using the native keypad. Record door movement, the actual loot and journal outcome, the door/keypad state after claim, and whether one leave/return or reload reoffers the three injected rewards. Without the information branch, the native graph can deliver the stash without a Succeeded journal root.
- **Earlier untracked claim.** The discriminating fixture is a genuinely claimed pre-Tower stash with the journal still Inactive and an observed native route that leaves the same door closed. Keep the pre- and post-Tower checkpoints and the actual claimed items. A previously claimed door that remains open is a useful negative control because QR19 should defer. An already-active or completed journal is separately protected by the entry checks. Neither inspected save is qualified for the closed-after-claim case.
- **Read-only qualification.** The existing installed S23 inspector prints Ready, Permit, Issued, Finished, Fault and the current journal match. Reading Entered separately distinguishes starting the phase from just claiming the wrapper. These values do not prove the door is streamed, a handler is live, or loot was delivered.
